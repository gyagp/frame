Conclusion — Section 1

The hardware executes the shared f16×f16→f32 case correctly through both native APIs. D3D12 LinAlg and Vulkan Cooperative Matrix produce the same maximum deviation at the same output element, while WARP is bit-exact against the CPU reference.

Capability reporting is less mature than execution: the AMD adapter reports no aggregate LinAlg tier but returns usable operation entries, while preview WARP reports Tier 1 and 192 supported wave configurations but over-advertises SINT8 and UINT8 support. Dawn filters those WARP types; its nonzero-config and advertised-config tests pass on the new preview. Numerical coverage is still narrow: this part directly verifies one AMD tuple and WARP's f16×f16→f32 path. Integer and FP8 tuples remain to be verified.

What had to change to get here

These changes describe how the historical stress run was made reachable. They are not all current product requirements; the corresponding upstream status is listed in Parts 1 and 6.

  1. Dawn's D3D12 tier gate. PhysicalDeviceD3D12.cpp enabled the feature only when LinearAlgebraTier >= TIER_1_0. That field reads NOT_SUPPORTED on this GPU (see Section 1), so Dawn exposed nothing and 43 of 44 cases skipped. The diagnostic branch ignored the tier, which was intentionally unsafe. Landed CL 333935 instead accepts a non-empty operation-specific configuration list as the preview capability signal; landed CL 335215 then removes configurations whose multiplication SUPPORTED bit is clear.
  2. Agility SDK disabled at build time. dawn_use_agility_sdk defaults to false, so the entire D3D12 subgroup-matrix block sits inside an inactive #ifdef and the first patch changed nothing. Rebuilt with dawn_use_agility_sdk=true.
  3. The D3D12 debug layer was forced on machine-wide (d3dconfig debug-layer-mode=force-on), which no Dawn flag can override. The retail debug layer caps at SM 6.9 and emits message 1243 for every SM 6.10 shader, which Dawn escalates to a device-lost error. Setting it to app-controlled took D3D12 from 3 to 15 passes.

What bypassing the checks revealed

With every D3D12/WARP capability check and per-config filter removed, the failures separate into four kinds. Note that “wrong result” is a failure just as much as a crash — but results for configurations whose SUPPORTED bit is clear are negative capability evidence, not failures of a supported feature.

  • Unsupported configurations can crash the driver. The configs historically filtered via CrashesOnRX9060XT (i32, u32, f32 and the 8-bit combinations at 16×16×16) fault with SEH 0xc0000005 on this RX 7900 XTX too. The D3D12 query returned shapes for these combinations while leaving SUPPORTED clear. CL 335215 fixes Dawn's capability handling so these tuples are not advertised or sent to pipeline creation.
  • A crash-then-hang on WARP. TiledMatrixMultiply at tile dim 2+ faults with an access violation and then never exits — killed at 151 s in isolation. Upstream describes this as "starts hanging"; the hang is the symptom and the access violation is the cause. It is excluded from the runs above, otherwise the whole report wedges.
  • Unsupported integer tuples also return wholly incorrect results. With the per-config filter removed, the integer configurations (i32/u32/i8/u8) do not merely round differently: in TiledMatrixMultiply at tile dim 1 the expected buffer holds int32 values such as -508, 4852, -90 while the GPU returns unrelated data (0x4A28631D and similar) — all 256 elements differ. These are the same configurations whose support bit is clear. This reinforces the need to filter them; it does not establish a correctness defect for an advertised, supported tuple.
  • Sub-ULP precision differences on f16. They are exclusively the multiply/accumulate suites; every non-accumulating case (construct, store, workgroup load/store, scalar arithmetic) passes. Decoding the compared buffers gives a maximum relative error of 5.9e-08, below f32 epsilon (1.19e-07), with max absolute difference 2.4e-07. AMD's hardware accumulates in a different order than Dawn's CPU reference and the test compares bit-exactly. The Section 1 GEMM avoids this only because its inputs sit on quarter boundaries, making the accumulation exact.

WARP 1.0.20-preview needed synthesised configs to test anything. In this historical stress run, WARP advertised no configurations, so the branch fell back to the SM 6.10 baseline shapes (f16→f16, f16→f32, f32→f32) when the granular query returned nothing. That turned the vacuous passes into real work: WARP then ran 19 of 20 non-tiled cases green, including QueryConfigsMustReturnNonZeroConfigs. The latest 1.65535.20-preview no longer needs this fallback.

Why default Vulkan runs skip so much

In a default upstream run without --run-suppressed-tests, Vulkan's skips are Dawn's own suppressions, not a hardware or driver limit. Of the 31 skipped there, 30 come from a single line repeated in three test bodies:

The consequence is that the core matrix-multiply case never executes on Vulkan in the default run. The diagnostic stress run above separately used --run-suppressed-tests to exercise those cases; these are two different views of the same checkout and should not be compared as one pass-rate table.

Why WARP 1.0.20-preview reported zero configs. That preview returned S_OK but left the payload and shape count at zero for every tested combination. Operationally that meant no configurations were reported; it was distinct from a feature query that returns an unsupported HRESULT. Dawn builds its config list solely from D3D12_FEATURE_LINEAR_ALGEBRA_MATRIX_OPERATION_SUPPORT (GatherLinAlgWaveMatrixMultiplySupports in D3D12Info.cpp), and that preview supplied no usable entries. This was not Dawn's two-pass NumShapes protocol being misused — the probe pre-allocated the shape array and still got 0 supported configurations from all 756 combinations, while the same WARP executed the GEMM correctly. That WARP advertised the coarse tier (TIER_1_0) but not the per-operation detail, which is the mirror image of the RX 7900 XTX, where the tier reads NOT_SUPPORTED but the granular query returns 16 usable configurations. WARP 1.65535.20-preview supersedes this result: all 756 queries succeed and 192 configurations report support, with the 8-bit over-advertisement noted in Section 7.

Conclusion — Section 2

The original Dawn path was blocked by capability reporting and setup, while the deliberately unfiltered path sent unsupported configurations to the driver. Out of the box, 43 of 44 cases skipped on the AMD GPU; after bypassing every guard, many invalid tuples crashed or returned unrelated data.

Three independent blockers had to be cleared, and none of them was the hardware: Dawn's D3D12 backend gated the feature on the same LinearAlgebraTier that reads NOT_SUPPORTED here; dawn_use_agility_sdk defaults to false, which compiled the whole subgroup-matrix block out and made the first patch a silent no-op; and a machine-wide forced D3D12 debug layer capped shaders at SM 6.9, which alone accounted for the difference between 3 and 15 passes. Each failure mode looked like "the GPU does not support this".

The actionable conclusion is narrower than the raw failure count. CL 335215 uses SUPPORTED as the capability boundary and removes the obsolete RX 9060 XT tuple suppressions; landed CL 335895 validates every HLSL matrix operation against the filtered list before pipeline creation. The remaining tile-dimension-32 suppressions are independent and stay in place. WARP 1.65535.20-preview now provides nonzero operation entries; after Dawn filters its unsupported 8-bit claims, the nonzero-config and advertised-config tests both pass. Its unforced f16 path and advertised explicit wave4, wave8, and wave16 paths are bit-exact. Unadvertised wave32 and wave64 requests fail pipeline creation with a misleading E_OUTOFMEMORY result.

How the wrong answer happened

Worth recording, because both failures produced plausible, self-consistent numbers rather than obvious breakage. Earlier revisions of this report claimed matrix was slower than FMA; that was a benchmark bug, not a property of the hardware.

  1. PCIe-bound inputs. A and B initially lived in an UPLOAD heap, so every K-step read across PCIe. All three variants were bandwidth-bound and measured nearly identically (~18 TFLOP/s), which looked like "the matrix instruction does not help."
  2. A baseline computing 12.5% of the work. The FMA kernel used a 4×4 per-lane patch, covering 2048 of the tile's 16384 outputs. It passed verification because all variants shared one output buffer and the preceding scalar run had left correct values in the untouched 87.5%. The baseline therefore looked ~8× faster than it was, and the matrix path looked slower than FMA.

Both are now fixed, and C is zeroed between variants so partial coverage cannot hide again. The general lesson matches Section 1: a benchmark, like a conformance test, needs a correctness gate that is independent of the previous run's state.

Conclusion — Section 3

The matrix instruction pays, and it is real silicon. Against a well-tuned FMA kernel — not a strawman — it is 1.7–3.3× faster, and the MMA_REPEAT probe puts marginal matrix throughput at ~145–150 TFLOP/s, at or above this part's ~123 TFLOP/s dual-issue fp16 figure and roughly 8× what the FMA path reaches. Nothing here is emulated, despite the driver reporting the linear-algebra tier as unsupported.

Neither API wins outright. D3D12 wave matrix beats Vulkan cooperative matrix on all five shapes by 12–21%, while Vulkan's plain FMA kernel beats D3D12's by 7–19%. Same tiling, same shapes, bit-identical results — so this is code generation and driver path, not hardware. Ship the matrix kernel and D3D12 is the faster target; ship the FMA kernel and Vulkan is.

The kernel is bound by data movement, not by the instruction. At ~61 TFLOP/s the full GEMM runs at under half the matrix units' issue rate, and that single fact explains every failed optimization: LDS row padding and register double-buffering are textbook GEMM techniques and both regressed here, because at a 128×128 tile the accumulators already hold ~128 VGPRs per lane and anything adding live state or LDS footprint costs more occupancy than it recovers in latency hiding.

Why the backends disagreed, and how it was fixed

The adapter advertises subgroupMinSize=32, subgroupMaxSize=64 on both backends, so a portable kernel cannot assume either. Probing what the backends actually compile to, with and without subgroup-matrix operations in the shader:

Dawn's D3D12 backend pinned wave32 for subgroup-matrix shaders; its Vulkan backend did not. A WGSL kernel written to ONNX Runtime's shipping layout — 4 subgroups of 32, each owning a 64×64 quadrant — therefore got only 2 subgroups on Vulkan and silently computed half the output tile. That is what the first run of this benchmark did: correct on D3D12, wrong everywhere on Vulkan, with no error reported by anything.

This is now fixable properly, and the fix is in the numbers above. gpuweb#5578 adds the subgroup-size-control feature and the WGSL @subgroup_size(n) attribute, which pins the size an entry point runs at (validated against the adapter's advertised range). Dawn implements it. Adding enable subgroup_size_control; and @subgroup_size(32) to the matrix kernel makes one portable kernel correct on both backends — no capability probing, no backend-specific tile layout, no silent halving.

Before the attribute existed, the only safe options were to detect the size at run time and reshape the tile around it, or to refuse the hardware. ONNX Runtime chose the latter, which is why Section 5's config table demands an exact subgroup-size match — a reasonable defence that @subgroup_size now makes unnecessary.

Pinning fixed correctness but did not move throughput: Vulkan's matrix kernel still measured 9.8 TFLOP/s at prefill-2048 against D3D12's 26.4. At the time that looked like a code-generation gap; it was not, and the next section gives the real cause.

Historical: why the first attempt was 2–5× too slow

WGSL has no unroll hint, and an array of subgroup matrices indexed by a loop variable has to be given an addressable home — which defeats the entire purpose of an accumulator that is supposed to live in registers. The cost was 2.1× on D3D12 and 5.3× on Vulkan. The asymmetry also explains what looked like a backend quality gap: Tint's SPIR-V path handled the spilled accumulators far worse than its HLSL path, so the same defect produced very different penalties and made Vulkan look structurally slower. With the accumulators in registers the two backends still differ by 8–21%, but in the same direction and by a similar margin to the native pair, so the defect was inflating the difference rather than creating it.

The lesson generalises past this kernel: a WGSL loop over subgroup matrices is not equivalent to the same loop in HLSL or GLSL, and nothing in the API surface signals the difference. It costs correctness nothing and performance almost everything.

Conclusion — Section 4

WebGPU is not the bottleneck. The original WGSL structure was. Once the kernel uses individually named accumulator values, Dawn stays roughly within 10% of the hand-written HLSL and GLSL on both backends; the observed 101% Vulkan point is measurement spread.

An earlier iteration of Section 4 concluded the opposite — that WebGPU surrendered most of the hardware, at ~40% of native on D3D12 and ~18% on Vulkan — and blamed the code Tint generates. That was wrong, and the fault was in the WGSL. The accumulators lived in an array<array<ResultT, 4>, N> indexed by loop variables; WGSL has no unroll hint, so the matrices needed an addressable home instead of registers. Writing them as individually named locals recovered 2.1× on D3D12 and 5.3× on Vulkan. The HLSL and GLSL never hit this because both have [unroll], so their identical-looking loops compile to constant indices.

Two other explanations were tested first and both failed: pinning the subgroup size changed throughput by ~2%, and matching ONNX Runtime's device toggles (disable_robustness and friends) gained ~5% on D3D12 and nothing on Vulkan. The asymmetry of the real cause also dissolved what looked like a backend quality gap — Tint's SPIR-V path punished the spilled accumulators far harder than its HLSL path, so one defect produced two very different penalties. With the accumulators in registers the two backends still differ by 8–21%, but by a margin comparable to the native pair — so the defect was inflating that difference rather than creating it.

Both traps are silent. Neither the subgroup-size mismatch nor the accumulator spill produces a warning, an error, or any signal in the API surface; the first yields wrong results on one backend only, the second yields correct results at a fraction of the speed. The subgroup-size one now has a proper fix — gpuweb#5578 added @subgroup_size, which this kernel uses, replacing the earlier workaround of probing the size and reshaping the tile around it. The accumulator one has no diagnostic at all, and is the more expensive of the two.

This also reframes Section 5. ONNX Runtime guards its subgroup-matrix kernel with an exact match on the adapter's subgroup-size range, which was a sound defence against the first trap before @subgroup_size existed — and which excludes this GPU. With the attribute available, that guard is no longer the only option.

Root cause

There is no cdb.exe on this machine and the process aborts before stdout is flushed, so the crash was caught by attaching a minimal Win32 debugger (avtrace.py) that keeps a history of unloaded modules. That last detail is what cracked it:

No driver frame, no dxcompiler, no D3D12 runtime — the whole stack is teardown. PlatformFunctions declares its Agility SDK COM interfaces before its DynamicLib members:

ComPtr<ID3D12DeviceFactory>       mDeviceFactory;        // declared first
ComPtr<ID3D12DeviceConfiguration> mDeviceConfiguration;

C++ destroys members in reverse declaration order, so ~DynamicLib calls FreeLibrary(d3d12.dll) — dropping the last reference to D3D12Core.dll — and only then releases the two ComPtrs. Release() reads a vtable that is no longer mapped. The landed fix declares the interfaces after mD3D12Lib, so reverse-order destruction releases them while their implementation is still loaded.

Those members exist only under DAWN_USE_AGILITY_SDK — the very define gate 3 had to turn on. So clearing the last gate is what exposed the bug, which is exactly why it looked like the kernel failing. This is an upstream Dawn defect when destruction of mD3D12Lib drops the process's last reference to D3D12Core.dll. The original ORT ReleaseEnv path reproduces that topology; a simpler Dawn end-to-end process retained another module reference and did not crash with the fix disabled.

Getting a name for that frame took one more step: the build passes /PDB: but not /DEBUG, so onnxruntime.dll ships no CodeView entry at all. A CMake reconfigure would have re-run FetchContent and destroyed the dawn-src patches, so MSBuild's own link command was replayed from its tlog with /DEBUG appended.

Gate 4 is worth noting for anyone tempted to route around gate 3 via Vulkan: Section 4 measured Dawn's Vulkan backend compiling subgroup-matrix shaders at wave64, where ORT's 4×32 kernel would silently compute half its output tile. ORT's exact-match check in gate 1 is guarding against exactly that, so relaxing it should stay restricted to backends that pin the subgroup size.

The leading candidate for that second factor is where the matrix is loaded from. And the Section 4 kernel proves Vulkan executes the matrix instruction itself at full rate. What is left is the combination — cooperative-matrix loads addressed at storage buffers.

Root cause: one memory operand in Tint

Every ablation of the k-loop had come back at 1–3% on Vulkan, which cannot be reconciled with a 2.56× gap. If no instruction accounts for the time, the time is not in the instructions. The test that broke the deadlock changed a count rather than an address: collapse the four cooperative A loads per k-step to one, keeping all sixteen multiplies and everything else intact. The asymmetry is total, and it is the shape of the answer. A loads dominate Vulkan and are nearly free on D3D12; B loads dominate D3D12 and are nearly free on Vulkan. The two are the same instruction on the same tile shape. What differs is the address space: A is read from a storage buffer, B from workgroup memory — exactly the split the standalone matrixga experiment above had already measured at 3.5–74×, and then wrongly acquitted.

The cause is in Dawn's SPIR-V writer. builtin_polyfill.cc hardcodes the memory operand on every cooperative-matrix access:

auto* memory_operand = Literal(u32(SpvMemoryAccessNonPrivatePointerMask));

Ordinary loads do not. MemoryAccessMaskForPointer() in the SPIR-V printer requests NonPrivatePointer only when the Vulkan memory model is enabled, the pointer is storage or workgroup, and its access is read_write. NonPrivatePointer requires the access to be coherent at device scope, so on RDNA3 it cannot be served from the per-CU caches. ORT binds the prepacked A tensor as var<storage, read> and issues four such loads per k-step — every one of them going past the caches to memory. That also explains the failed experiment above: pinning A to a cache-hot address measures nothing when the load is not permitted to use the cache.

The fix gives both cooperative sites the same rule as ordinary accesses. Fourteen lines in Dawn, no change to ORT, and D3D12 is untouched because it never goes through SPIR-V. Only the load site matters for this kernel: A is read-only so the flag is dropped, while buf_b in workgroup memory and the read_write output buffer keep it.

Why the hardware differs is inference, not measurement. NonPrivatePointer asks for coherence at device scope. This does not weaken the case for the change, it re-bases it. The defect is vendor-independent and is one of consistency: ordinary loads request NonPrivatePointer only for read_write pointers, while the cooperative ones requested it always — including for a buffer that nothing can write during the dispatch, where device-scope coherence establishes nothing. What varies by vendor is only the price. The two other GPUs measuring 1.00× is the evidence that removing it regresses nothing.

An earlier draft of this report claimed the operand was invalid SPIR-V whenever the Vulkan memory model was disabled, since NonPrivatePointer requires the VulkanMemoryModel capability and the printer declares that capability only under that option. That was wrong, and is withdrawn. Subgroup matrix already requires the memory model everywhere it matters: Dawn refuses the feature when the toggle is off (PhysicalDeviceVk.cpp), re-checks it in DeviceVk.cpp, defaults the toggle to true on that backend, and Tint asserts it in the printer when emitting a subgroup matrix type. The capability is therefore always declared, and this is a performance and consistency issue rather than a correctness one.

The experiment also surfaced a correctness result that matters more than the timings. The f16-accumulate variant fails the CPU reference check on every shape: 6.3% maximum relative error at K = 3072, rising to 19.3% at K = 8192. The error grows with the accumulation depth, which is what distinguishes genuine f16 accumulation loss from a conversion bug. This is the configuration ONNX Runtime ships for quantised inference, and it is one of the fifteen Section 1 never verified. ORT's own source already hints at it — the kernel is restricted to accuracy level 4 on Apple for “precision issues with subgroupMatrixMultiplyAccumulate”.

A caveat on the magnitude: the benchmark's inputs are quarter-integers in [-1, 1] accumulated over the full K, which is a harsher accumulation pattern than real activations. The trend with K is the trustworthy part, not the absolute percentage.

One more thing fell out of this. The samples in d:/r/dawn never received the teardown fix from Section 5, and its D3D12 runs exit with a segmentation fault while its Vulkan runs exit cleanly. Applying the same three-line change made D3D12 exit 0. That is independent confirmation of the root cause in a second, clean checkout — and that checkout, unlike the FetchContent copy, is a real git tree to raise the change from.

One caveat on all Vulkan numbers: model_benchmark does not validate output, so correctness on this arm rests on the pinned subgroup size and Section 4's CPU-verified runs of the same configuration, not on a fresh numerical check.

Conclusion — Section 5

The kernel works and is worth having, but only for prefill, only above about one tile of prompt, and it moves end-to-end latency far less than the prefill number suggests.

At 512 prompt tokens prefill throughput rises 2825 → 5141 tok/s (+82%) and time to first token nearly halves, 181 → 100 ms. At 128 prompt tokens it loses 7%: the workgroup tile is 128×128, so that prompt is a single M-tile and there is no second tile to amortise the setup over. The crossover sits somewhere between the two, and this evaluation did not map it — two prompt lengths on one model is enough to establish the sign of the effect, not its shape.

Decode is untouched by construction. A single-token step has M = 1, below the kernel's kMinMForTileOptimization = 4 gate, so it never reaches the subgroup-matrix path and stays on MatMulNBits in both arms. Measured decode differences are ±1.5%, which is run-to-run spread.

That is what caps the end-to-end result. Generating 128 tokens, prefill is only 5% of the loop at 128 prompt tokens and 16% at 512, so an 82% prefill win becomes an 8% end-to-end win (1112 → 1029 ms), and the 7% prefill loss becomes a 2% end-to-end loss. The kernel is worth enabling for long-prompt, short-generation shapes — summarisation, RAG, classification — and is close to irrelevant for chat-style decode-dominated use.

The prepack pass, long suspected as the hidden cost, is not one: 0.4 ms against 69.5 ms of GEMM, 0.6% of the kernel it feeds.

Before CL 330695, backend choice appeared to matter more than the kernel. The same kernel through Dawn's Vulkan backend measured 2.6× slower on the GEMM and 2.23× slower on prefill, against only 1.24× on decode, which never touches it. That was never a Vulkan weakness in general: Section 4's kernel reaches 41–52 TFLOP/s on the same backend. The cause was a single hardcoded memory operand in Dawn's SPIR-V writer. Tint tagged every cooperative-matrix access NonPrivatePointer, which demands device-scope coherence and so prevents the per-CU caches from serving it. ORT binds its prepacked A tensor read-only and issues four such loads per k-step, all of them uncached. Gating that flag the way ordinary loads already gate it — Vulkan memory model, storage or workgroup, and read_write — takes Vulkan prefill from 2,299 to 5,032 tok/s and the GEMM from 18.6 to 45.7 TFLOP/s, reaching 1.00× of D3D12 with no change to ORT and no effect on D3D12. The f16→f16 configuration remains a real but secondary cost at 10–37%.

That recovery is AMD's alone. The same pair of builds measures 1.00× on an RTX 5080 and 0.99× on an Arc 140V, and the standalone bench shows why: a storage-buffer cooperative load already runs at 48.2 TFLOP/s on the RTX 5080 without the fix, against 2.19 on RDNA3. The flag costs nothing on those parts, so there is nothing to recover. The defect itself is vendor-independent — asking for device-scope coherence on a buffer nothing can write during the dispatch — but only hardware whose caches below that scope are non-coherent pays anything for it.

Two readings in this report had to be withdrawn to get there. The storage-buffer A loads were the cause, having been acquitted by two tests that changed where A was read from and at what address but never how many cooperative loads were issued; pinning an address proves nothing about a load that bypasses the cache. With the fix in place, ORT's D3D12-scoped gate is no longer correct — on Vulkan the kernel is now worth 1.67× over DP4A.

The same experiment produced the more consequential finding: f16 accumulation fails the reference check on every shape, with error growing from 6.3% at K = 3072 to 19.3% at K = 8192. That is the configuration ORT ships, and Section 1 never verified it.

The complete path is still not reachable in a stock ORT build. It took eleven source patches across ONNX Runtime and Dawn, plus a staged Agility SDK and two DLLs dropped in the run directory. Three of those patches fix outright Dawn defects: one crashes any Agility-SDK build at exit, one makes a compiled-in Vulkan backend fail to load, and one costs every Vulkan cooperative-matrix load from a storage buffer a factor of two to twenty. The Vulkan load fix landed in CL 330695, and CMake Agility support landed in CL 326715. ORT still needs to update its Dawn pin, enable the default-off option, and pick up the teardown fix before a stock CMake-built D3D12 build can run this kernel.

The old LinAlg query model is deprecated

The current D3D12 runtime draft formally deprecates D3D12DDI_FEATURE_VERSION_LINEAR_ALGEBRA_0115_1; new drivers should report the 0115_2 feature version exclusively. The older preview model mixed native-shape discovery and acceptance in one operation query: wave-matrix multiply returned a NumShapes/Shapes array together with SupportFlags. That ambiguity is directly relevant to the AMD failure investigated here: a successful call and non-empty shape array did not mean the type combination was accepted in a shader; the SUPPORTED bit remained authoritative.

QuestionDeprecated 0115_1 model Current 0115_2 model
Is this exact type/shape supported? The old operation-specific structure could return native shapes while also returning support flags, requiring the caller to interpret both correctly. D3D12_FEATURE_LINEAR_ALGEBRA_MATRIX_OPERATION_SUPPORT takes one application shape as input and returns an explicit supported result and operation metadata.
Which configurations are native? Shape discovery was embedded in operation support. The old construction DDI reported only one minimum tiling and could not express multiple native tilings. D3D12_FEATURE_LINEAR_ALGEBRA_OPERATION_ENUMERATION returns a flat native-configuration list using a count-then-fill sequence.
Compatibility The runtime still loads 0115_1 drivers and translates new granular queries where possible. Native enumeration cannot be synthesized completely from an old driver; it returns DXGI_ERROR_UNSUPPORTED, so applications must fall back to targeted granular queries or reject the configuration.

Dawn is currently on the compatibility side of this transition. The tested Agility SDK 721.3 headers still expose the older combined NumShapes/Shapes query, so landed CL 335215 checks SUPPORT_FLAG_SUPPORTED before retaining those shapes. Once Dawn moves to headers with the split APIs, it should use operation enumeration for native discovery and the granular query for validation. That migration does not make the current fix obsolete: old SDK/driver compatibility still needs the authoritative flag check.

LinAlg is broader than Vulkan v1 (KHR) and overlaps much of v2 (NV), but the abstractions are not equivalent. LinAlg's strongest unique features are its thread-scope matrix-vector+bias path, outer-product/atomic-accumulate path, and driver-managed optimal weight layouts. Vulkan v2 (NV) is stronger for general tensor addressing, reductions, callback-defined element transforms, and flexible workgroup-scoped matrices. KHR v1 remains the portable common denominator.

Conclusion — Section 6

No single API is a strict superset. LinAlg is stronger for thread-scope matrix-vector+bias, outer product, atomic accumulation, optimized weight layouts, and cross-vendor D3D12 tiering. Vulkan v2 (NV) is stronger for flexible workgroup-scoped matrices, reductions, per-element callbacks, and tensor layout/view addressing, but remains an unratified NVIDIA extension. Vulkan v1 (KHR) is the smaller, ratified, cross-vendor Vulkan baseline and the portable target Dawn uses today.

Dawn does not expose all of LinAlg's useful features. It deliberately exposes a small, cross-backend subgroup-matrix intersection that maps to D3D12 wave matrices, Vulkan KHR cooperative matrices, and Metal simdgroup matrices. That is a sound portable baseline, but it leaves major inference and training capabilities unavailable. The highest-value future additions are likely capability-rich configuration reporting, casts/use conversion, FP8/bfloat16, and a portable answer for threadgroup/workgroup scope. Thread-scope matrix-vector+bias, outer product, atomic accumulation, and optimal weight layouts are valuable but currently D3D12-specific enough that exposing them would require a wider WebGPU design, not just another Dawn backend mapping.

Microsoft WARP Forced [WaveSize(N)] access violation WARP 1.0.20-preview faulted with 0xC0000005. On 1.65535.20-preview, forced wave4, wave8, and wave16 each compile, dispatch, and match the CPU reference exactly for f16×f16→f32. Those are the explicit wave sizes advertised for this operation. Wave32 and wave64 are not advertised and fail pipeline creation with E_OUTOFMEMORY. RESOLVED explicit WaveSize works for advertised configurations; the remaining poor HRESULT for unsupported sizes is not a subgroup-matrix support blocker
Microsoft WARP Extend the bit-exact oracle beyond f16 inputs On WARP 1.65535.20-preview, 16×16×16 f16×f16→f16 and f32×f32→f32 both matched the CPU reference with zero mismatches and zero maximum absolute error. The existing f16×f16→f32 path is also bit-exact. Current WARP does not advertise FP8, and Dawn filters its known-invalid SINT8 and UINT8 claims under issue 527049636. RESOLVED all usable floating-point families are numerically covered; invalid or unadvertised families are not oracle targets
